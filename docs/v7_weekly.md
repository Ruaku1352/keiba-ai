## 仕様書で確認したこと（結果はいつ届くか）

JV-Data 仕様書の「データ提供タイミング・提供単位」より。

**蓄積系 `RACE`（いま `fetch --option 1` で取っているもの）**

| 曜日・時刻 | 届くもの | データ区分 |
|---|---|---|
| 木曜 16:30 / 20:00ごろ | 出走馬名表（枠番・馬番なし） | 1 |
| 金曜・土曜 12:00ごろ | **翌日の**出馬表 | 2 |
| **月曜 14:00ごろ** | **確定レース情報（成績・払戻）** | 7 |
| 不定期 | レース情報の変更・修正 | — |

- **蓄積系では、土日の成績は月曜 14:00 ごろにまとめて届く。** 土曜の夜や月曜の深夜に取っても
  成績が無かったのは、この仕様のとおり。速報成績（区分3〜6）は蓄積系の `RACE` には入らない。
- 月曜が祝日の3日開催のとき、確定成績が月曜に来るのか火曜に来るのかは仕様書に書かれていない。
  次の3日開催で、火曜の午後に `fetch --option 1` をして確かめるのが確実。

**速報系（`JVRTOpen`）なら当日の結果が取れる**

| データ種別 | 中身 | 提供 | 指定するキー |
|---|---|---|---|
| `0B12` 速報レース情報（成績確定後） | RA・SE・HR。払戻・3着まで確定 → 5着まで → 全馬着順 → コーナー通過順まで、確定のたびに追加 | 土日、レース確定後。1週間 | 開催日単位 `"YYYYMMDD"`、またはレース単位 `"YYYYMMDDJJKKHHRR"` |
| `0B15` 速報レース情報（出走馬名表〜） | 上に加えて出走馬名表・出馬表の時点のもの | 木曜〜。1週間 | 同上 |
| `0B11` 速報馬体重 | 馬体重（発走の約1時間前） | 土日 | 同上 |
| `0B14`/`0B16` 速報開催情報 | 天候馬場状態・出走取消・競走除外・騎手変更・発走時刻変更 | 金土日 | `0B14` は開催日単位 |

レコードの形は蓄積系と同じ RA/SE/HR（同じ構造体で読める）。データ区分が 3〜6 の行として届き、
月曜に確定成績（7）が届けば、既存の重複解消（確定度の高い方を残す）で置き換わる。

必要な作業（**まだ実装していない**）:
1. `jvlink.py` に `fetch-rt --date YYYYMMDD --spec 0B12` を足す：`JVInit` → `JVRTOpen("0B12", "20261010")` →
   `JVGets` で最後まで読む → `JVClose`。ダウンロード待ち（`JVStatus`）は不要（`JVRTOpen` は受信が終わってから戻る）。
   読んだ RA/SE/HR を今の CSV に追記する（`_seq` は続きから）
2. `jvmap` は区分 5・6 を確定レースとして使っているので、変換側は変更不要（区分3・4＝5着までしか確定していない版は使わない）
3. 運用：土曜の最終レースの後（17時以降）に `fetch-rt --date <土曜>` → 日曜の予測に土曜の結果が入る。
   日曜の夜に `fetch-rt --date <日曜>` → 月曜（祝日）の予測に日曜の結果が入る
4. `0B16`（取消・騎手変更）や `0B11`（馬体重）も同じ仕組みで取れるが、馬体重を待たない方針なので不要

これを入れると、本番の特徴量が学習（前日までの結果）と同じになり、下の 3(2) の差は無くなる。

## 毎週の手順

v6 の実測：train・predict・replay とも約2分。results も約2分（生データの読み込みが大半）。

### 準備（1回だけ）

1. リポジトリ直下に `local_settings.json` を作る（`local_settings.example.json` をコピーして書き換える。
   `.gitignore` 済みなのでコミットされない）:
   ```json
   {
     "google_service_account_file": "C:\\Users\\tensu\\keiba\\secrets\\google_service_account.json",
     "spreadsheet_id": "（シートの URL の /d/ と /edit の間）",
     "entry_sheet": "評価入力",
     "record_sheet": "記録"
   }
   ```
   環境変数 `KEIBA_GOOGLE_KEY`・`KEIBA_SHEET_ID` でもよい（こちらが優先）。
2. （任意）シートの見出しに「更新日時」という列を足すと、プログラムが書き換えた行にその時刻が入る。
   予測し直したときに、どの行がいつ更新されたか分かる

## 結果の照合のきまり（判断したこと）

- 予測 CSV（`data\predictions\predict_*.csv`）は全部読み、レースごとに**発走時刻より前に作った最後のもの**を使う
  （作成時刻はファイル名の `_YYYYmmdd_HHMMSS`、発走時刻は RA の発走時刻）。発走後に作ったものしか無いレースは照合しない
- 練習（`replay_*.csv`）は「練習（replay）」として別に数える。同じレースの replay が複数あれば、
  モデルの学習終了日がレース日より前のものを優先する。そういうものが無ければ
  「練習（replay）・参考外」（モデルがそのレースの結果を見ている）として通算に入れず、記録シートにも書かない。
  10/4 の replay は、`train --until 2026-09-30` のモデルで作ったものなら「練習」に入る
- 的中の判定は払戻データの的中組（同着で複数あればそのすべて）が BOX の馬番に入っているか
- 取消・発走除外・競走除外（異常区分 1〜3）の馬を含む買い目は返還される。投資は実際に走った頭数 n で
  n×(n−1)×(n−2)×100円。競走中止・失格は返還されない
- 熱い基準は 50,000円で固定（返還で投資が減っても変えない）
- 仮の収支 = 的中した払戻の合計 − 投資
- 期待値の 4.7%（3.85〜5.71%）は v6 の `diagnose weight` の「代用」のプール値（本番と同じく出馬表の時点の予測）
- 「記録」シートには、照合できたレースの全頭について レースID・日付・レース名・馬番（実際の）・馬名・
  予測確率・予測順位・着順（取消・中止などは文字）・単勝オッズ・馬体重 を書く。本番予測と練習で同じレースが
  あれば本番予測を書く

## 3(2) 同じ週末の前の日の結果が入らない影響（diagnose weekend）

validate の5 fold で、検証期間の重賞を3つの条件で予測する（馬体重はすべて代用＝本番の条件）。

| 条件 | 学習の特徴量 | 検証の特徴量 | 意味 |
|---|---|---|---|
| A | 前日まで | 前日まで | 今の検証（＝速報を取り込めば本番もこれ） |
| B | 前日まで | 週末より前 | 今の本番（速報を取らない） |
| C | 週末より前 | 週末より前 | 学習側を本番に合わせる案 |

- 「週末より前」= 1日も空かずに続く開催（土日、土日月）の初日より前の結果だけ。
  作り方は as_of="day" の除外単位を「その連続開催の初日」にするだけ。
  ただし過去の各レースのペースの z 化は、本番と同じく「そのレースの前日まで」で行う
  （`pace.STANDARDIZE_DAY_COL`。この列が無いときの動作は変わらない。as_of race/day の特徴量が変更前と完全一致することを確認済み）
- **この作り方が本番の予測の経路と一致することをテストで確認した**（土曜の結果を入れずに日曜を
  `build_prediction_features` で作ったものと、セル単位で全列一致）
- 影響を受けるのは週末の2日目以降の重賞だけ（初日は A と B で同じ）。その割合も表示する
- 比べ方：同じ重賞レースでの熱い当たりの対応のある差（B − A、C − A、C − B）と AUC
- **提案（結果を見てから決める）**：
  - B − A がほぼ 0 なら、今のまま（何もしない）
  - 差が無視できないなら、第一案は**速報系 `0B12` を取り込む**（本番を学習に合わせる。上の作業）。
    本番が A と同じ条件になり、学習はそのまま使える
  - 速報の実装をしない場合の第二案が C（学習も「週末より前」で作る）。`train` に `--as-of weekend` を足し、
    予測の経路は今のまま（同じ週末の結果が無い状態）で一致する。C − B がプラスならこの案に意味がある

## 4 学習開始 1995年 vs 2003年（diagnose start-year）

**判定ルール（結果を見る前に固定。コマンドも最初にこれを表示する）**

- 主指標：重賞・上位6頭BOX の熱い当たり（5 fold の検証レースをプール。**馬体重は代用＝本番の条件**）
- 同じ検証レースを両方のモデルで予測するので、**対応のある比較**（Newcombe (1998) 法10 の差の 95% 区間）を使う
- 差（1995 − 2003）の 95% 区間の**下限が 0 を超えたら 1995年を採用**。そうでなければ 2003年のまま
- AUC・実際の馬体重での達成率は参考として表示するだけで、判定には使わない
- 比べるのはこの1組だけ。as_of=day。検証の fold・学習方法（検証期間で early stopping）は validate と同じ

ご提案のルールからの変更点と理由：
1. **差の区間を「対応のある比較」にした。** 同じ2,002レースを2つのモデルで予測するので、2つの結果は強く相関する
   （ほとんどのレースで両方とも外れ、両方とも当たる）。別々の標本を仮定する区間（v4/v5 で使った two_proportion_test）は
   この相関を無視するので幅が広すぎ、本当の差を見逃しやすい。対応のある区間は「片方だけ当たったレース」の数で
   差を測るので、同じデータでも正しく狭くなる。下限 > 0 という基準の厳しさ（有意水準 5% 相当）は同じ
2. **主指標を馬体重「代用」の条件にした。** 本番は出馬表の時点で予測を確定する方針になったため
   （v6 の diagnose weight で実際の馬体重との差は p=0.82 と確認済み）

検出力の目安：熱い当たりは各モデル 90〜100件（4.7% × 2,002レース）。差の区間の幅はおおよそ
「片方だけ当たったレースの数」で決まり、それが合わせて 40〜80件なら ±0.6〜0.9% ほどになる。
下限が 0 を超えるには、1995年の方がそれ以上はっきり良い必要がある。
「差が出なければシンプルな今の設定」という結論になりやすいルールで、それで良いと考える。

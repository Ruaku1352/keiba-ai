> 開発記録。最新の状況と使い方はリポジトリ直下の README を参照。

**戦略の探索はしない。** v4で確定した戦略（重賞のみ・上位6頭の3連単BOX・選別なし）が、
2021年8月以降を含む JRA-VAN のデータでも成立するかを確かめるための取得・変換・再検証。

## SDK を読んで分かったこと（依頼書との差分を含む）

| 項目 | 内容 | 対応 |
|---|---|---|
| **JVOpen の終了時刻** | 依頼書は「開始時刻だけ」とあるが、インターフェース仕様書では `RACE` について `"開始-終了"` 形式で**終了時刻も指定できる**（TOKU/DIFF/HOSE/HOYU/COMM は不可） | `--from` にそのまま渡せる。ただしこれは**データの提供時刻**でレース日ではないので、レース日での絞り込みは `jvmap.build_dataset(start=, end=)` で行う |
| **JVSkip** | 「蓄積系データは1ファイルにレコード種別1種類」。`RACE` には巨大な3連単オッズ(O6)・票数(H1/H6)も入っている | 不要種別の先頭1件を見たら `JVSkip` でファイルごと飛ばす。取得時間が大きく変わる |
| **ダウンロード完了待ち** | 「ダウンロード完了を待たず JVGets を呼ぶと予期しないエラーが起きうる」。サンプルも `JVStatus` で待っている | 読み込み前に `JVStatus` がダウンロード数に達するまで待つ。そのうえで `-3` も待って再試行 |
| **option=4 のダイアログ** | 「ダイアログ無し」だが**初回だけはダイアログが出る** | 初回のセットアップは画面の前で実行すること |
| **地方・海外** | `RACE` の RA/SE は「中央のみ」と明記。地方・海外は `DIFF` 系で来る | 依頼書どおり防御的に `JyoCD 01〜10` かつ区分 `A/B` 以外で絞る |
| **単勝オッズ** | SE の単勝オッズが確実に入るのはデータ区分 `7`（月曜確定）のみ | 学習は 5/6/7 を使うが、オッズは特徴量に入れないので影響なし |
| **後3ハロン** | 「過去分は後4ハロンだけ入って後3ハロンが初期値のことがある」 | 後4Fで代用せず欠損として扱う（別の量なので） |
| **3連単の払戻** | 同着用に6枠ある | 1番目の組の払戻を使う（Kaggle 版も1列だった）。的中組数を `3連単的中組数` に残す |
| **HR のフラグ配列** | `[単勝,複勝,枠連,馬連,ワイド,予備,馬単,3連複,3連単]` の9要素 | 列名は1始まりで、3連単 = `[9]` |
| **構造体ファイル** | 後で定義されるクラスを型注釈で先に参照している（226行目） | Python 3.14 は通るが3.13以前は `NameError`。ファイルは書き換えず、`from __future__ import annotations` 相当のフラグでコンパイルして読む |

### 文字コード：MidB2S を cp932 版に差し替える

SDK の `MidB2S` は `shift_jis` でデコードするため、「髙」「﨑」などが `errors="ignore"` で**黙って消える**。
読み込んだモジュールの `MidB2S` だけを cp932 版に入れ替えている（ファイルは書き換えない）。
`SetDataB` は呼び出し時にモジュールの `MidB2S` を探すので、これで全フィールドに効く。
`test_sdk_parses_se_fields_and_keeps_cp932_chars` が「差し替えると残る／差し替えないと消える」の両方を確認している。

それでも識別には名前を使わない。馬は `KettoNum`、騎手は `KisyuCode`、調教師は `ChokyosiCode`。

## データ区分の扱い（`jvmap.apply_data_kubun`）

同じレース・同じ馬が「出馬表 → 速報 → 月曜確定」と何度も届き、過去レースの訂正も後から届く。
**レコードヘッダーのデータ作成年月日の古い順**（同じ日なら取得した順）に見て：

- 区分 `0`（削除）→ そのキーを消す
- それ以外 → 既存より確定度が**同じか高ければ**置き換える（同じなら作成日の新しい訂正版が勝つ）

**取得した順で並べない理由**：取得の順番は提供の順番と一致しない。直近1ヶ月を先に取ってから
全期間のセットアップをすると、「1987年のレースの訂正版（2026年作成）」が先に、
「元の版（1987年作成）」が後から入る。取得順だと古い元の版が訂正版を上書きしてしまう
（v5 初版はこの実装だった。`test_kubun_newer_make_date_wins_regardless_of_fetch_order` で修正を確認）。

**作成日だけで決めない理由**：確定(7)の後に、作成日の新しい速報(3)が別ファイルで届くことがありうる。
確定版を速報で上書きしないよう、確定度でも比べる。

そのうえで学習・検証には区分 **5/6/7** のレースと馬だけを使う。3/4 は3着・5着までの馬しか含まないので、
使うと出走頭数や着順が欠ける。9（中止）は除外。

## Kaggle 形式への対応（`jvmap`）

| 論理名 | 列名 | JRA-VAN 側 | 注意 |
|---|---|---|---|
| race_id | レースID | 年+場+回+日+R | Kaggle と同じ12桁（月日は含めない） |
| horse | 血統登録番号 | KettoNum | 表示用の名前は `馬名表示` |
| jockey | 騎手コード | KisyuCode | 表示用は `騎手名略称` |
| trainer | 調教師コード | ChokyosiCode | 表示用は `調教師名略称` |
| grade | リステッド・重賞競走 | GradeCD | A→G1 / B→G2 / C→G3 / D→G（下の注意） |
| surface / turn | 芝・ダート区分 / 右左回り・直線区分 | TrackCD | コード表 2009 から変換。`内外区分` も作る |
| going | 馬場状態1 | Siba/DirtBabaCD | 芝なら芝、ダートならダートの方 |
| horse_weight_diff | 場体重増減 | ZogenFugo + ZogenSa | 符号を結合。999=計量不能・空白=初出走は NaN |
| time | タイム | Time | `"1345"` → 94.5 秒 |
| last3f | 後３Ｆタイム | SE HaronTimeL3 | `"345"` → 34.5 秒 |

`config.COLUMN_CANDIDATES` には `騎手コード` `調教師コード` を**末尾に**足しただけなので、
Kaggle データ（`騎手` `調教師` 列がある）の挙動は変わらない（`test_kaggle_column_resolution_unchanged`）。

**異常区分** 1〜5（取消・発走除外・競走除外・中止・失格）は除外、6（落馬再騎乗）と7（降着）は残す。

**コードはラベルに変換した**（良/稍重、芝/ダート など）。LightGBM にはどちらでも同じだが、
重要度や表を人が読むときに分かりやすいため。

### グレードの対応

| GradeCD | 意味 | 既定の変換 | 重賞扱い |
|---|---|---|---|
| A / B / C | G1 / G2 / G3（平地） | G1 / G2 / G3 | ○ |
| D | グレードのない重賞 | G | ○ |
| F / G / H | J.G1 / J.G2 / J.G3（障害） | J.G1 …（Kaggle と同じ表記） | ✕ |
| L | リステッド | L | ✕ |
| E | 重賞以外の特別 | （空） | ✕ |

**障害重賞は重賞に含めない（確認済み）。** Kaggle データでは障害重賞が `J.G1`〜`J.G3` という
別の値になっていて、v4 の重賞定義（G1/G2/G3/G）に入っていなかった。JRA-VAN 側も同じ表記・同じ扱いにした。
`--jump-as-flat` は使わない（障害重賞を平地と同じ G1〜G3 として数える、比較用のオプション）。

### 払戻：不成立・特払・返還は除外しない（v4 と同じ条件）

v4（Kaggle）ではこれらのレースを除外していなかったので、**既定は除外しない**にした（開発者の判断）。
件数は `build` に「不成立・特払・返還あり（除外しない）」として表示される。
`--exclude-irregular` を付けると除外する（依頼書の当初の指示どおりの条件）。
`--keep-irregular` は既定と同じ動作で、互換のために残してある。

なお不成立・特払で3連単の的中組番が `000000` のレースは、設定に関係なく払戻なしになる（当たり目が無い）。

## 特徴量の入力差し替え

- **4角相対位置**：文字列パースをやめ、SE の `Jyuni4c` を直接使う（`corner.attach_corner_from_columns`）。
  分母は RA の**公式出走頭数**。race_result の行数で数えると、競走中止で除いた馬のぶん頭数が減って
  相対位置が1を超えることがあるため。相対位置から先（脚質スコア・展開）は既存ロジックをそのまま使う
- **ペース**：ラップからの再計算をやめ、RA の公式 `HaronTimeS3` / `HaronTimeL3` を使う。z 標準化は既存のまま
- **公式脚質判定**（`KyakusituKubun`）：今回レースの判定なのでそのレースの値はリーク。過去走だけで
  `公式脚質_過去平均` `_逃げ率` `_追込率` `_前走` `_レース内平均差` を作る
- **DM予想**（JRA-VAN のマイニング予想）：依頼書どおり初回は**特徴量に入れない**（`DM_予想順位` 列は残すが未使用）

その日の結果である列（4コーナー順位・脚質判定・公式3F）は `_` で始まる名前にしてある。
`features.add_all_features` は `_` 始まりの列を最後に必ず削除するので、過去集計に使った後で
特徴量に紛れ込むことがない。

## ⚠ v1〜v4 にあったリークを1件修正した（調教師）

新しい入力形式で「同一レース内リーク」のテストを書いたところ、**調教師通算勝率**が引っかかった。

調教師は1レースに複数頭を出すことがある。`cumsum - 自分` だと、同じレースで馬番が若い
同厩馬の結果が「過去」として混ざる。例えば同厩2頭のうち1頭目が勝つと、2頭目の調教師勝率に
その勝ちが入っていた（＝2頭目は勝っていないという情報が漏れる）。

```
旧: [nan, 1.0, 0.5, 0.333, 0.5]   ← R1 の2頭目が同じレースの1頭目の勝ちを見ている
新: [nan, nan, 0.5, 0.5,   0.5]
```

`leakfree.past_rate_excluding_race` を追加した。仕組みは
`(キー単位の累積) - (キー×レース単位の累積) = 前のレースまでの分`。
騎手は1レース1頭なので本来は起きないが、データの誤りに備えて同じ版に揃えた。

**影響**：調教師の通算勝率は数百走の平均なので、1レース分の混入による値のずれは小さい。
ただし v4 の数字はこのリークを含んだまま出ているので、**v4 と v5 の差にはこの修正の効果も含まれる**。
Kaggle データで v4 を回し直せば、修正の効果だけを切り分けられる。

**途中で止まったら、同じコマンドをそのまま再実行する**（`--from` と `--option` も同じ値で）。

- 読み終えたファイル名は `data\jvlink\progress_RACE_4_19860101000000.txt` に1行ずつ記録される。
  再実行するとこれを読んで、読み終えたファイルを `JVSkip` で飛ばし、続きから読む
- 記録は「CSV への書き出しが終わってから」行うので、停電などで止まっても記録とデータがずれない
- 途中まで読んでいたファイルは頭から読み直す。そのぶん CSV に同じレコードが2回入るが、重複解消で1件になる
- ダウンロード済みのファイルは JV-Link 側に残っているので、ダウンロードもやり直しにならない
- 完走すると進捗ファイルは自動で消え、`state.json` に最新ファイル時刻が保存される
- `-402` / `-403`（ファイル異常）、`-502`（通信エラー）、`-503`（ファイルが見つからない）は、
  そのファイルを消して**自動で3回まで開き直す**。それでも止まったら時間をおいて再実行
- Ctrl+C で止めてもよい（書けた分を保存し、JVClose してから終わる）

**所要時間の目安**（実測ではなく見積もり。最初の1時間の進捗ログで見直すこと）：

| 段階 | 目安 | 根拠 |
|---|---|---|
| ダウンロード | 数十分〜数時間 | 回線次第。`ダウンロード n/M` の進み方で残りを見積もる |
| 読み込み | 30分〜1時間程度 | 1ヶ月分（約5,600件）が3秒 ＝ 約2,000件/秒。全期間は RA 約15万・SE 約200万・HR 約15万件 |

進捗は5万件ごとに `n 件 {...}（ファイル 読了数/全体数）` と表示される。

**ディスク**：CSV は合計 1GB 程度（SE が大半）。JV-Link の保存先（JV-Link の設定画面で確認できる）にも
ダウンロードしたファイルが数GB以上たまるので、空き容量を確認してから始めること。

**メモリ**：`build` は SE 約200万行を文字列で読む。`pyarrow` が入っていれば pandas 3 が省メモリな
形式で持つので、`requirements.txt` どおり入れておくこと。

## v5 の成功判定（`validate.recent_period_check`）

**2021年8月以降**の重賞・上位6頭BOXの達成率を、v4 のプール値（82/1,337 = 6.13%）と
`two_proportion_test` で比べ、**有意に低いか**を見る。

- 有意に低い → 「崩れた」と表示（無理に条件を変えて合わせにいかない）
- 有意に低くない → 「維持」と表示

依頼書の指示どおり、「下限5%」のような固定値では判定しない。
v4 の熱い当たり数 82 は 6.13%×1,337 からの逆算値。区間 4.97〜7.55% と一致することを
`test_v4_reference_interval_is_consistent` で確認してある。

あわせて H1（重賞 > 平場）も同じ期間で検定する。

### 「維持」の読み方に注意

「有意に低くない」は「同じだと確認できた」ではない。2021年8月以降の重賞は約5年分（680レース前後）
なので、達成率6%前後なら差の95%区間は**±2.2ポイント程度**になる（v4 の1,337レースと比べた見積もり）。
つまり達成率が 4% 程度まで下がっていても「有意に低くない」と出うる。**区間の下限がどこまで下がりうるか**を
`v4との差の区間` で必ず見ること。


- **取得ループ**（偽の JV-Link）：`-3` で待って再試行、`-3` が続けば上限で止める、不要種別は JVSkip、
  `-1`（該当なし）はエラーにしない、ダウンロード完了まで JVGets を呼ばない、
  `-402` でファイル削除、**どんな例外でも JVClose する**
- **データ区分**：速報→確定で確定が残る、確定の後に遅れた速報が来ても上書きしない、削除が効く、
  中止・速報段階のレースを除外、地方・海外を除外
- **変換**：タイム・オッズ・斤量・馬体重増減の単位、トラックコード、グレード、12桁のレースID、
  不成立・特払・返還の除外
- **リーク**（JRA-VAN 形式で再確認）：未来のレースの着順・コーナー順位・脚質判定・3Fを書き換えても
  過去行が不変／自分のレースだけ書き換えても自分の行が不変／**同厩馬の結果が調教師成績に混ざらない**
- **SDK**（`JVSDK_DIR` があるときだけ）：仕様書どおりの長さのダミーバイト列を構造体に通し、
  RA/SE/HR の値・cp932 の文字・フラグの列番号を確認。取得→CSV→変換の往復

## 取得が遅いときの切り分け（`fetch_timing.csv` と `bench`）

全期間のセットアップで、SE のファイルだけが1件あたり約0.3秒かかる現象が出た（1986年2月の SE で約6分）。
同じ月の RA・HR は数秒、前日の通常データ（option=1）は1件あたり約0.5ミリ秒だった。

### ファイルごとの内訳

`fetch` は保存対象のファイルを読み終えるたびに、次の1行を表示し、`data\jvlink\fetch_timing.csv` にも追記する。

```
[  12/5084] SEVM1986029920230808160615.jvd SE 1,150件 352.1秒 = JVGets 350.2 / -3待ち 0.0(0回) / 解析 0.1 / 書出 0.0 / その他 1.8  [JVGets 1回: 前半0.4ms 後半610.3ms]
```

- **JVGets**：JV-Link の呼び出しにかかった時間。JV-Link はプロセス内で動くので、その中の処理もここに入る
- **-3待ち**：ダウンロード中で待った時間と回数
- **解析 / 書出**：こちらのコード。手元で測ると SE 1件あたり約0.08ミリ秒
- **前半 / 後半**：そのファイルの最初の100件・最後の100件の JVGets 1回あたりの時間。
  後半ほど遅ければ、ファイル内の読む位置に比例して遅くなっている

### bench（先頭のファイルだけ読んで比べる）

本番の CSV・進捗とは別のフォルダ（`data\jvlink\bench\`）に書くので、本番の再開記録には影響しない。
JV-Link を2つ同時に開かないよう、本番の取得は止めてから実行すること。

```powershell
py -m src.jvlink bench                          # 最初の SE ファイル1つ（既定のバッファ 2048）
py -m src.jvlink bench --buffer-size 110000     # 公式サンプルと同じ大きさ
py -m src.jvlink bench --method read            # JVGets の代わりに JVRead で読む（速さの比較用）
py -m src.jvlink bench --profile                # 関数ごとの時間（cProfile）も出す
```

### bench の結果と、既定値を 2048 にした理由

セットアップ用の SE ファイル（`SEVM19860199…`、3,226件）での実測：

| バッファ | 合計 | JVGets 1件あたり | 解析・書き出し |
|---|---|---|---|
| 110,000（公式サンプル） | 296.5秒 | 91.65ms | 1秒未満 |
| **2,048** | **110.4秒** | **34.09ms** | 1秒未満 |

2点から分けると、JVGets 1回 ≒ **約33ms（大きさに関係しない）＋ 約0.53ms/1万バイト**。
2048 にするとバッファ由来の部分はほぼ消える（約1ms）。残りの約33msは JV-Link の中の処理で、こちらでは減らせない。
通常データ（option=1）は同じ 110,000 で1件約0.5msだったので、**セットアップ用ファイルのときだけ**
JV-Link の1回あたりの処理が重い。`-3` は0回、ファイル内の位置による増加もなかった。
通常データ（option=1）で1986年分を取る方法は「該当データなし」で使えなかった。

2048 で足りるかは、`RACE` に含まれる全種別のレコード長（仕様書）で確認した：

| 種別 | 長さ | 2048 で |
|---|---|---|
| RA / SE / HR（保存する） | 1,272 / 555 / 719 | 収まる |
| JG / O1 / O2 | 80 / 962 / 2,042 | 収まる（読み飛ばす） |
| O3〜O6・H1・H6・WF | 2,654〜102,890 | 切り捨て。先頭2バイトで種別が分かれば JVSkip するので問題ない |

保存する種別が切り捨てられるバッファ（1,272 以下）は、起動時にエラーにする。

### JVRead について

JVRead は JV-Link の中で SJIS → Unicode に変換して文字列で返す。こちらでは cp932 でバイト列に戻してから
構造体に通すので、変換できない文字があると位置がずれうる。テストでは JVGets と同じ値になることを確認したが、
**本番には使わず速さの比較だけ**に使う。

### Ctrl+C で止めたとき

書けた分を CSV に書き出して JVClose してから、トレースバックを出さずに終わる。
後始末の間は2回目の Ctrl+C を無視する（後始末が途中で打ち切られないように）。

`-3` の待ちは 0.05 秒から倍々に伸ばし、1秒で頭打ちにした（以前は毎回1秒）。
